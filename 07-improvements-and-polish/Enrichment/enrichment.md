# Week 7 Enrichment: Improvements And Polish

This enrichment is optional. Use it when you want more context for improving, documenting, and preparing your project for release.

## Optional Topics

### Refactoring

Refactoring means changing code structure without changing external behavior. It is useful when code is hard to read, duplicated, or risky to change.

- Read: [IBM: What is code refactoring?](https://www.ibm.com/think/topics/code-refactoring)
- Read: [freeCodeCamp: Code refactoring best practices with examples](https://www.freecodecamp.org/news/best-practices-for-refactoring-code/)

### Code Quality

Code quality is about whether code is understandable, testable, and safe to change. In this course, the practical goal is clear code that still runs and can be explained during the final presentation.

- Read: [Google Engineering Practices: What to look for in a code review](https://google.github.io/eng-practices/review/reviewer/looking-for.html)

### Maintainability

Maintainability means future changes can be made without breaking the app or confusing the developer. A maintainable project has clear files, obvious commands, small functions, and documented limitations.

- Read: [DORA: Code maintainability](https://dora.dev/capabilities/code-maintainability/)

### Documentation

Documentation helps another person understand what the project is, how to run it, and what is still missing. A short `README.md` is enough for this course if it is accurate and useful.

- Read: [Diataxis documentation framework](https://diataxis.fr/)
- Read: [Write the Docs: A beginner's guide to writing documentation](https://www.writethedocs.org/guide/writing/beginners-guide-to-docs/)

### Changelogs

A changelog records important changes between versions. Release notes are similar, but usually more focused on what changed for users or reviewers.

- Read: [Keep a Changelog](https://keepachangelog.com/en/1.1.0/)

### Release Planning

Release planning decides what belongs in the next version and what waits. In this course, the release plan is simple: finish selected improvements, document known limitations, and prepare for Week 8 deployment.

- Read: [GitHub Docs: Managing releases in a repository](https://docs.github.com/en/repositories/releasing-projects-on-github/managing-releases-in-a-repository)

### Semantic Versioning

Semantic versioning is a common version number format: major, minor, and patch. It is enrichment for this course because the main required output is release notes, not formal version management.

- Read: [Semantic Versioning Specification](https://semver.org/)
